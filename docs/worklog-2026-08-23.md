## 3. 도구(씬) 검토 (12종, v0.14.0)

### 3-1. 단청 — 해시가 사실상 무작위가 아니었다

`FNV1a(...) % 2`가 문제였다. FNV 소수 `0x01000193`이 홀수라 곱셈이 **최하위 비트를 보존**한다.
즉 `% 2`의 결과는 "입력 문자 코드의 홀짝 합"과 정확히 같아진다.

| 지표 | 수정 전 | 수정 후 |
|---|---|---|
| 질문 끝에 물음표를 붙였을 때 답이 뒤집힘 | **100%** | 49.8% |
| 4시간 창이 넘어갈 때 붉↔청 교대 | **90.9%** | 49.9% |
| 붉/청 비율 | — | 49.9% |

murmur3의 `fmix32` 마무리 섞기를 붙여 상위 비트를 하위로 접어 넣었다.
같은 결함이 `timeOfDay.js`의 인사말 선택(`% 10`)에도 있어 함께 고쳤다.

### 3-2. 메뉴 룰렛 — 비복원 모드가 안내에 닿지 못했다

'전부 나왔어요! ↺ 제외 취소로 되돌리기' 안내는 이미 있었지만 **도달 불가능**했다.
🍟 감자튀김이 제외 대상이 아니라 후보 풀이 0이 되지 않기 때문이다.
실측으로 다른 메뉴가 모두 나온 뒤 **22회 연속 감자튀김**이 아무 설명 없이 반복됐다.
감자튀김을 뺀 나머지가 비면 그 시점을 한 판의 끝으로 본다(더블탭 확정은 사용자가 직접 고른 것이므로 통과).

### 3-3. 검증하여 문제 없음

러시안룰렛 조건부확률 · 크로코/팝업 잔여 개수 · 뽑기/빙고/빙고판/로또의 비복원 추첨 ·
조 배정 Fisher-Yates와 조 인원 배분 · 전 씬 localStorage 손상 방어 · 재진입 시 오버레이 참조 초기화.

## 4. 정적 폴백 제거 (v0.14.0)

캔버스 자리의 `#fallback`(2026-08-17 도입)이 **정상 이용자에게 "도리 화면을 불러오지 못했습니다"로 번쩍였다.**
`animation-delay: 600ms` 뒤 페이드 인하고 `BootScene.create()`에서 제거하는 구조인데,
실측 부팅 완료가 **약 1.4초**다. 도입 당시 기록한 '정상 부팅 200ms 이내'는 CDN 시절 값으로,
라이브러리를 자체 호스팅(약 1MB Phaser)한 뒤로는 맞지 않게 됐다.

- **시간으로 실패를 추측하면 성공한 화면에 실패 문구를 보여 주게 된다.** 실패 안내는 실패를 감지한 뒤에만.
- 스크립트 미실행 대비는 폴백 **뒤에** 생긴 소개 섹션(`#site-info`)이 이미 담당하고 있었다.
- `#game`의 `position: relative`는 Phaser DOM 오버레이(입력창)의 기준이라 남겼다.

## 5. 사다리 공정성 (v0.15.0)

### 진단

다리를 무작위로 뿌려서는 균등해지지 않는다 — 인접 전치 셔플의 혼합 시간이 Θ(n² log n)이라
화면에 담을 수 있는 행 수로는 원리적으로 부족하다. 20만 판 실측:

| 인원(행) | 최대 편차 | 비고 |
|---|---|---|
| 6명(16행) | **48.6%** | 출발0 → 결과0 **24.3%** vs 결과5 **8.8%**(균등 16.7%) |
| 5명(14행) | 32.1% | |
| 4명(12행) | 13.5% | 기본값이 '커피 1 + 통과 3'이고 커피가 0번 칸 고정이라 **1번이 4번보다 커피 살 확률 약 29% 높음** |

부수적으로 왼→오른쪽으로만 훑는 생성 방식 때문에 **경계0이 경계1보다 1.72배 많은 다리**를 가졌다.

완화책 스윕도 해 봤다 — 컬럼 순서 무작위화만으로는 48.3% → 49.1%로 거의 개선이 없고,
편차 6%대까지 내리려면 31행·확률 0.8(행 간격 18px)이 필요해 화면이 빽빽해진다. **완화로는 풀리지 않는 문제.**

### 해법 — 결과를 먼저 뽑고 다리를 역산

룰렛이 이미 쓰던 원칙을 사다리에도 적용했다.

1. **위 `rows − n`행** — 보기용 무작위 다리(밀도 0.42·경계당 최소 1개 보장은 그대로). 공정성은 여기에 기대지 않는다.
2. **균등한 목표 순열**(`rng.shuffle`) — 공정성의 근거는 오직 여기다.
3. **아래 최대 n행** — 홀짝 교환 정렬(odd-even transposition sort)로 목표까지 보정.
   n라운드면 어떤 순열이든 정렬되고, 한 라운드의 다리는 **경계 번호의 홀짝이 같아 반드시 두 칸 이상 떨어진다**
   (한 점에서 세 갈래가 되는 일이 구조적으로 불가능).
4. **남는 행** — 같은 경계에 위아래 한 쌍(갔다 되돌아오기 = 항등)으로 채운다.
   없으면 판 아래에 빈 띠가 생겨 사다리가 중간에 끊겨 보였다.

| 인원 | 이전 | 이후 |
|---|---|---|
| 6명 | 48.6% | **1.0%** |
| 5명 | 32.1% | 0.7% |
| 4명 | 13.5% | 1.4% |

(20만 판. 1σ가 약 0.5%이므로 통계 오차 수준.) 목표 순열 불일치 0 · 한 점 세 갈래 0 · 비순열 0.
평균 다리 24.4개로 밀도는 이전(약 33개)과 비슷하다.

**화면의 정직함은 그대로다** — 그려진 다리가 진짜 다리이고, 경로는 그 다리만 따라가며, 거꾸로 짚어도 맞는다.

## 6. 빙고 범위 불일치 (v0.15.0)

사회자(빙고 뽑기)는 최대 숫자 10–99 자유 입력인데 참가자 빙고판은 프리셋 다섯 개뿐이었다.
그러면서 안내에는 "사회자와 같은 범위여야 합니다"라고 적혀 있었다 — 사회자가 40을 고르면 맞출 방법이 없었다.

빙고판에 직접 입력(25–99)을 열었다. 5×5가 성립하려면 마지막 구간에도 숫자가 다섯 개 남아야 하는데
(`max − 4×ceil(max/5) ≥ 5`), 25–99 중 그게 안 되는 값은 **26 · 27 · 28 · 31 · 32 · 36 여섯 개뿐**이고
나머지 69개는 전부 만들 수 있다. 안 되는 값은 이유와 함께 가장 가까운 가능값을 안내한다(`cardOk`/`nearestOk`).
저장 로더 검증도 `PRESETS.includes` → `cardOk`로 바꿨다.

## 7. 문안 정정

- **`read-ladder-fairness.html`이 dori를 잘못 설명하고 있었다** — "dori처럼 다리를 전부 공개하되 **결과 라벨을 나중에 붙이는**".
  실제로는 결과가 처음부터 보인다. 진짜 방어 장치는 "이름을 모두 채우고 시작을 누르므로 판을 보고 줄을 고를 수 없다"는 점이다.
- 룰렛 후보 수 "2개부터 16개까지" → 최대 16개. 하한 2는 강제되지 않는다 — 모두 지우면 감자튀김 한 칸만 남는다.

## 8. 검증 방법

- **분포 검증**: 알고리즘을 Node로 이식해 20만 판 시뮬레이션 → 실제 소스를 브라우저에서 `import`해 3만 판 재확인 →
  **배포본 URL을 직접 `import`해 3만 판 최종 확인**(6명 최대 편차 2.50%, 3만 판의 1σ ≈ 1.29%).
- **카드 생성 전수 검증**: 가능한 69개 범위 × 자유칸 2가지 × 40판 — 열 구간·중복·자유칸 모두 정상.
- **스모크**: 딥링크로 씬 12종 진입 — JS 오류 0건.
- **정적 검사**: 수정한 JS `node --check`, HTML 태그 균형, `[임시]` 마커 0건.

## 9. 오진했다가 바로잡은 것

| 오진 | 실제 |
|---|---|
| 핀볼이 씬을 나갈 때 `physics.world.timeScale=2.1`이 남는다고 판단하고 수정까지 넣었다 | **누수 없음.** 가상 시간에서 `scene.start()`가 실행되지 않아 **내가 대입한 값을 되읽고 있었다.** 실시간 재검증 결과 Phaser는 씬 재시작마다 `World`를 새로 만든다(`동일객체=false`, 재진입 `timeScale=1`). 넣었던 수정은 되돌렸다 |
| 빙고판 B열이 8·5·9·6·4로 전부 한 자리라 편향을 의심 | Phaser `RandomDataGenerator.frac/shuffle`을 이식해 20만 회 검사 — 최대 편차 0.80%, 우연 |
| 헤드리스 스크린샷에서 허브·안내 페이지가 깨져 보였다 | 최상위 `--window-size=390`이 약 800px로 레이아웃한 뒤 잘라낸 것. **390px 폭 iframe 안에 넣고 부모를 찍어야** 실제와 같다 |
| 건너뛰기 링크가 포커스에 반응하지 않는다 | 가상 시간에서는 **CSS 트랜지션이 얼어붙는다**. `transition:'none'` 후 확인하면 정상 |

> 교훈: `--virtual-time-budget`은 **정적 렌더 확인에만** 쓴다. 씬 전환·입력·트랜지션이 걸린 검증은 실시간으로.
> 또 Node의 파일 리다이렉트 stdout은 버퍼링되어 로그가 늦게 보인다 — 검증 서버는 `appendFileSync`로 기록한다.

## 10. 남은 항목

- 사다리 보정 구간(아래 n행)은 한 라운드의 다리가 같은 홀짝 경계에만 놓인다.
  분포에는 영향이 없지만 눈이 밝은 사용자에게는 규칙성으로 보일 수 있다 — 무작위 분해로 바꾸는 안은 보류.
- 사다리 경계별 다리 수는 여전히 최대 1.3배까지 차이 난다(4명 기준). 공정성과 무관한 미관 문제.
- `docs/responsive-design.md` §10 "Phaser가 DPR 기본 처리" 서술 부정확 — 2026-08-01 로그에서 넘어온 미해결 항목.
